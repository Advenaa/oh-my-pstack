### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.** For "land the stack", "ship it", "enable merge when ready", or the second half of a stack that **Babysit** already drove to green.

This is the half after `skill://poteto-mode/playbooks/babysit.md`. Babysit makes a stack mergeable. Shipping decides what is actually safe to merge, then lands it. Green is not safe, and the gap between those two words is where this playbook lives.

1. **Verify every PR independently before it lands.** One independent canonical `reviewer` **Bounded session** per PR, not batched, each exercising the real surface through the installed control capability against parent versus head. GitHub CLI (`gh`) is the forge, and every PR operation goes through it. Each verifier returns a frozen `PASS`, `PASS+NOTES` or `FAIL` tied to the exact head SHA. The root checks the evidence, then posts the accepted verdict on the PR so the record outlives the chat; when the root lacks that mutation surface, it starts a separate canonical `mechanical` participant through the **Bounded session** protocol to post the exact frozen text. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. The PRs below it are the run and the top one is the ceiling. A verified PR above an unverified one is not landable, because merging it would pull the gap in underneath it. Report the ceiling as a PR number and say what breaks the chain. A PR whose branch neither holds nor needs the code below it can move onto trunk and land on its own, and it needs a fresh verdict first, since its old one ran with that code beneath it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a rebase moves every PR above it to a new SHA without failing a single check. Compare `git patch-id` at the verdict SHA against the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR, with `gh pr merge <pr> --squash`. A PR whose base is still its parent's branch merges into that branch, not trunk, so read the PR back for the result (`gh pr view <pr> --json state,mergedAt,baseRefName`). A merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Arm `gh pr merge <pr> --auto` only on a PR whose verdict covers its current head, because auto-merge lands whatever head its branch holds at that moment.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. No restack, no speculative pushes, and no stack-wide submit that reaches downstack into PRs that are mid-merge. Watch the run with the queued watcher from `skill://poteto-mode/playbooks/babysit.md` (`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`) as a **One-shot watcher**, starting a fresh watcher after any verdict you act on, until it reports `COMPLETE` at the ceiling. `ADVANCE` is progress, not termination. A base that moves to trunk when its parent merges is expected, not damage. If a merge stalls, find out why before you change anything, because a stalled queue and a broken stack look identical from the outside. Independent work gets re-parented onto trunk and shipped on its own.
6. **Never enable GitHub auto-merge across a whole stack at once.** Only the root targets protected trunk. Every child targets its unprotected parent branch and already reads `CLEAN`, so GitHub would merge children into parents immediately and collapse the stack into itself. Arm one PR at a time from the bottom, as step 4 says. If a previous agent armed the whole stack, disarm with `gh pr merge <n> --disable-auto` and confirm the field is back off.
7. **Do not read `autoMergeRequest` as proof that a merge is armed.** It stays off until the queue reaches that PR, so an unarmed reading is meaningless and acting on it leads to re-submitting branches that were already fine. Confirm arming from the PR's own state after you set it, and if you cannot, say so rather than inferring it.
8. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1, not a judgment call you make at 3am.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you armed and how you confirmed it, what landed, and what the next gap needs.
