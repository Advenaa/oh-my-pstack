### Autopilot-full

**You own the verdicts and merges, never the PR implementation. One owner runs each PR from build to merge-ready, and nothing merges without a clean swarm verdict from verifiers that never wrote the code.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. The job is a queue of independent PRs handed over to drive to merged with full autonomy. Each PR's owner carries implementation through merge-ready; the root owns verification, countersigns, and the authorized merge.

A verdict covers one patch, and green CI covers one head. The patch-id rule in `skill://poteto-mode/playbooks/shipping.md` carries a lane's result to a new head, and every new head still needs its own green CI.

1. **Mark the operator's items and honor state-then-wait.** The grant covers the queue's items only, so items the operator names as hers and PRs outside the queue stop at merge-ready. She reviews and she clicks, and no owner merges one. When she asks for the protocol or the plan to be stated, deliver the statement and stop, because a statement is not a go. Execution starts only on her explicit go.
2. **Start one owner per PR with the full lifecycle.** Use the active adapter's **Long-lived owner** protocol with canonical `owner` role, one `task` spawn per PR, and match that owner's model and reasoning level to its job per **Match the model to the job**. Fix the forge once for the program, and it is `gh` for every PR operation. Each owner owns build, its PR opened early per `skill://poteto-mode/playbooks/opening-a-pr.md` so CI and bots run alongside the work, with that playbook's review gates landing on the finished code rather than gating the opening, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical Bugbot triage per `skill://poteto-mode/references/bugbot-triage.md`, direct **unslop** cleanup, and a restack onto current trunk. The root starts Comment Sicko review and Babysit watchers, relays their frozen findings to the owner for fix-forward, and performs the authorized merge. The restack always precedes babysit and never waits for drift or conflicts. Fix rounds stay on the base the owner already pushed unless trunk conflicts, breaks CI, or lands a known concurrent change to the same files, because each rebase restarts CI. Code is ready only after **unslop** and the Comment Sicko pass, so the full swarm runs on finished code, and the owner reports every head, the code-ready head first, then merge-ready once self-proof, CI, and babysit are done. Run the repo's checks for the touched paths on the committed head before the code-ready push and before any later push that needs a verifier. Step 4 gates the root-owned merge.

   Assume the host dies. Keep the run's `decisions.tsv` trail per the **show-me-your-work** skill, never committed, a row for what changed and who owns it, returned with its reports, and push each finished unit before starting the next so a replacement owner can resume. Whoever spawns a subagent records its id, state, and a stuck-after runtime from past runs of its kind in that trail, so the root can probe it if the parent dies. Force-push only your own branch, `--force-with-lease` pinned to the SHA you last pushed or took over, and on a push you did not make, stop and report to the root.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained, one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch, so each PR lands on its own. A short private stack for a genuinely dependent split is not this playbook's work and runs through **Autopilot-stack**, which owns the one stacking exception.
4. **Swarm-verify every merge-ready head before its merge.** At the owner's merge-ready head SHA, fan out parallel independent verifiers per the **swarm** skill and aggregate to one verdict. The fan-out mechanics live there; do not restate them. The lanes: re-run the gates at that SHA; prove the load-bearing behavior live through the installed control capability for the surface the change touches; audit the receipts and the diff, distrusting the PR body. The live lane is the floor, and a verdict without it is not clean. No merge without the root's clean verdict. Findings go back to the owner for fix-forward, and the new head gets a fresh verdict sized to what moved: a full swarm for new behavior, a redesign, or a large new diff, a single verifier for a rebase, a conflict resolution, or a minor fix, and none for a wording-only change.

   Block a PR only for a problem you can show, with a failing run at the head or a doc line the PR made wrong. A problem the PR's base already has, whether trunk or the PR below it in a stack, does not block unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks, and everything else goes in a follow-up.
5. **On a clean verdict the root merges and starts a fresh owner for the next item.** The root merges only what a clean verdict covers, at a head tested on the trunk it lands on, because green CI alone never authorizes a merge. Merge prep rebases the verified patch onto current trunk, the merge-ready report is made at that trunk-current head, and the swarm verdict pins that SHA; the owner reports the new head and waits for green CI. Any rebase from here, at merge prep or after it, follows the patch-id rule in `skill://poteto-mode/playbooks/shipping.md`, because a new head voids the verdict unless the patch-id is unchanged, and one that moved the patch-id goes back through step 4.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land, and a failing install means the rebase must repair it. When trunk changed a caller of the patch or something it depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase past merge prep, hold the PR and sequence the colliding work before merging.

   The root squash-merges the PR and starts a fresh owner session for the next self-contained queue item. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for her click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten), or a loosened allowlist entry, needs a verifier's proof and then your fresh countersign, granted only after that proof. Absorbing values that already landed on main is drift, not a raise. Under a grant that covers approvals, that countersign is the approval, and the owner's trail row points at it for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass a branch-protection approval the forge enforces, because no countersign covers it.

   On the operator's go, arm an **Autonomous run** whose exit condition is no delegated work left, with a one-hour root heartbeat, because long runs drift and agents stall silently. Each tick re-reads this playbook from trunk, uses the active adapter's poll/wait evidence, and fixes drift, such as an unreported head or an unrecorded agent, by having that owner record it, because drift is a gap in the record, not a stall. It probes every agent, down to the leaf lanes, and judges each by its side effects, because status text and summaries can hide a stuck child. An agent is stuck when it errors, cannot start turns, or shows nothing new past its stuck-after runtime, and so is an owner that has neither pushed nor written a trail row by the first tick; one waiting on you or the operator is not stuck, so answer it. Replace a stuck agent at once, without waiting for its stop to land. A child never re-arms itself. A tick that changed nothing for the operator stays quiet, and one that changed something ends by catching them up per the **ketchup** skill. When merges batch, run a retro pass and a post-merge bot-comment sweep.
7. **Stand down instantly on the operator's stop.** Her hold or stand-down reaches every owner as a zero-writes order immediately. Each owner reports where it stands and holds its brief until she releases it.

**Reply:** catch the operator up per the **ketchup** skill, covering each PR's owner, state, and head SHA with a link to the PR, its verdict and the swarm that produced it, what merged and which fresh owner took each next item, countersigns granted and why, open operator gates, parked follow-ups, and where the collected decision trails live.
