### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one reviewed set of verified PRs she lands herself.** For "autopilot-stack", "stack them, don't ship", "build the stack, I'll land it". The sibling of **Autopilot-full**, which it runs with the merge removed. The owner loop and the verification gate are the same; only the terminal differs. There a clean verdict authorizes the root's merge. Here it adds the PR to the reviewed set, and nothing auto-ships.

1. **Run the owner loop unchanged.** Use one active-adapter **Long-lived owner** session per PR with canonical `owner` role, and match its model and reasoning level to the job per **Match the model to the job**. It owns build, its assigned branch, self-proof (gates, CI, receipts), skeptical Bugbot triage per `skill://poteto-mode/references/bugbot-triage.md`, and direct **unslop** cleanup. It reports the branch tip and intended parent, rebases and force-pushes its own branch, and never retargets a base. The root starts Comment Sicko review and Babysit watchers, relays their frozen findings to the owner for fix-forward, and owns every base ref. Owners parallelize when the work is self-contained. Every owner keeps a `decisions.tsv` trail per the **show-me-your-work** skill, never committed, returned in its report.
2. **Audit on root-controlled timing.** The root runs audit ticks roughly every 30 minutes using the active adapter's poll/wait evidence: owner liveness, progress, and protocol adherence. Every tick's prompt names this file, so no tick runs without the no-merge rule in front of it. A child never re-arms itself.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On her stop, every owner takes an immediate zero-writes hold.
4. **Verify at STACK-READY.** The owner reports STACK-READY with the exact head SHA, verified and green at that head. The root swarm-verifies that SHA, fan-out per the **swarm** skill: parallel independent verifiers re-running the gates at that SHA, a live runtime floor over the load-bearing behavior, and a receipts-and-diff audit that distrusts the PR body. The swarm aggregates to one verdict. Findings go back to the owner for fix-forward, and only a clean verdict admits a PR.
5. **Add on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict adds the PR to the reviewed set, in verified order or an order the operator specified. A PR that builds on another joins the chain directly above its parent, and an independent PR stays on trunk in the same set. The handover happens once every PR in the set is verified and green at its current head, and after that handover nobody pushes without the operator's go.
6. **Single writer on base refs, parallel writers on builds.** A PR is stacked only when it genuinely builds on another PR, which is the one exception to Autopilot-full's step 3, and the **PRs** paragraph in `skill://poteto-mode/playbooks/opening-a-pr.md` covers when that holds. It bases on that PR's branch instead of trunk, set at creation with `gh pr create --base <parent-branch>` or afterwards with `gh pr edit <n> --base <parent-branch>`. Those base refs are the whole topology, and a reviewer reads them bottom-up, so only the root changes one, because a retarget moves the chain under every open review. An owner pushes only its own branch, `git push --force-with-lease` after an `ls-remote` check, and reports its tip and intended parent. An owner that thinks its base is wrong asks the root instead of editing it.
7. **Absorb drift at the root, then re-verify what moved.** While the queue is still being built, each stacked PR rebases onto its parent PR's branch, a PR based on trunk rebases onto trunk, and a new head on a lower PR restacks everything above it. The root absorbs trunk movement by sequencing the chain rebase from the bottom, the root PR first. An owner rebases and pushes its own branch, including a conflict fix in its own files, and the root decides the order. A rebase rewrites every SHA above it and voids the verdicts at the old SHAs, so compare `git patch-id` at each verdict SHA against the new head, and a PR whose patch-id the restack leaves unchanged keeps its verdict. Anything that actually drifted goes back through step 4 before delivery. Once the handover has happened, drift absorption stops with every other push, and a restack becomes the operator's call. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign, and absorbing drift of landed values is not a raise.
8. **Deliver the set.** The deliverable is one reviewed set of verified PRs, linear where the PRs depend on each other and rooted at trunk, readable bottom-up through its base chain, every PR carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it, with her own clicks or with merge-when-ready she arms herself, from the bottom up, because a child whose parent branch has no required checks merges into that parent as soon as it reads clean.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the lowest and topmost PR in the set, each PR with its verdict in place of what merged, and anything parked or excluded with the reason.
